# P4.6 — Railway staging preparation

**Status: prepared locally, not deployed.** Owner approval is required before committing, pushing, creating the service, or generating a public domain. This is a development/staging deployment of the public marketing site and fictional `/demo` pages, not the P15 production launch. Do not connect Ayadatak to Wanasatna resources or attach `ayadatak.com`.

## Exposed routes and security boundary

- `/`: marketing site. `/demo`, `/demo/demo`, `/demo/sakeena-demo`: public fictional, noindex clinic previews; other `/demo/[slug]` values resolve to 404.
- `/health`: minimal liveness response, no database read, no credentials or service detail. Configure this as Railway's deployment healthcheck path; it does not prove database readiness or provide ongoing monitoring.
- `/dashboard-demo` and `/dashboard-demo?preview=1`: browser-local prototype, available with `next dev` only. Production builds return 404 before rendering the editor or preview. No mock identity or staging password is used. Keep this route disabled until P5 provides server-verified authentication and explicit authorization. Do not rely on navigation hiding. The marketing root is noindex/nofollow and omits the final-domain canonical/OG URL unless `AYADATAK_DEPLOYMENT_ENV=production` is deliberately set in a separately approved production launch.
- No application middleware/proxy, Server Actions, or public database/admin API exists. `src/lib/server/` remains `server-only`; P4.5 actor-protected operations fail closed and are not imported by routes. Never add `NEXT_PUBLIC_` database or auth secrets.

## One-service setup after owner approval

1. Review the full dirty tree and create a dedicated staging commit/branch locally. Include the approved P3/P4 source, migration history, docs and P4.6 guard together as appropriate, but exclude `.env.local`, generated Prisma client, `.next`, logs and machine files. Run the checks below before pushing. Do not force-push or rewrite existing history.
2. In the existing Railway Workspace, create an **Ayadatak** project/service from the correct Ayadatak GitHub repository, not Wanasatna. Choose a dedicated staging environment and deployment branch (for example `codex/ayadatak-staging` only if the owner creates/approves that branch). Disable PR environments and auto-deploys from unrelated branches to limit spend. No Dockerfile, Railway PostgreSQL, worker, volume, or second service is needed.
3. Let Railpack detect Node/npm. The package declares Node `^20.19.0 || ^22.12.0 || ^24.0.0`; prefer Node 22 LTS and verify the detected build version in logs. Build command: `npm run build` (Prisma Client generation followed by webpack Next.js build). Start command: `npm run start -- --hostname 0.0.0.0 --port $PORT` on Railway's Linux shell. Railway injects `PORT`; do not hard-code 3000. Set Healthcheck Path to `/health`. Do **not** set a pre-deploy command or run `prisma migrate deploy` in build/start.
4. Set `AYADATAK_DEPLOYMENT_ENV=staging` in Railway for this build. Never set it to `production` without a separately approved P15 launch. Leave `NODE_ENV=production` as Railway/Next's normal build/runtime mode (do not override it to `development`). No database variables are needed for the current public fixture pages: leave `DATABASE_URL` and `DATABASE_URL_UNPOOLED` **unset**. Do not copy `.env.local`. If a later approved server feature needs Neon, add `DATABASE_URL` as a server-only Railway secret using the correct pooled development connection; keep `DATABASE_URL_UNPOOLED` solely for separately authorized direct CLI migrations, never as an automatic service migration setting. Never expose or log either value. No `NEXT_PUBLIC_` secrets.
5. Select one replica in a region appropriate for the intended audience and future Neon locality; compare latency and residency requirements before selecting. Railway currently offers EU West (Amsterdam) and Southeast Asia (Singapore) among its regions. Do not provision a database on Railway. Generate a temporary `*.up.railway.app` domain under service networking only after the owner authorizes the deployment. Leave final Ayadatak DNS/domain untouched.
6. Check build/deploy logs for Node version, successful Prisma generation/build, start and `/health` 2xx. Confirm `/`, `/demo`, `/demo/demo`, `/demo/sakeena-demo` render and unknown demos return 404; confirm both `/dashboard-demo` variants return 404, including direct requests and with query parameters. Check that no credential appears in logs or browser bundles. Review service metrics and workspace estimated usage after a day and a week; set a budget alert/hard limit appropriate to the existing workspace, noting a hard limit can stop other services.

## Cost and operational notes

Use one service and one replica. Builds are not billed for CPU/RAM on Railway, but a continuously running Next.js service consumes metered RAM/CPU even when idle, plus egress. Current published Railway rates and included credits depend on the owner's plan; check the workspace's actual plan before deploying. Serverless sleep can reduce idle spend but introduces a wake-up delay and may conflict with an always-immediately-available preview; decide after measuring. Do not change Wanasatna's environment or workspace-wide limits without reviewing their impact.

## Local gate and sources

Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `node scripts/staging-smoke.mjs`, `npm audit`, and `git diff --check`. The smoke script starts/stops a local production server and checks public pages, `/health`, unknown demos, and both denied editor variants. Typecheck and build must run sequentially. All listed checks passed locally on 2026-10-29; the first sandboxed build encountered a transient Windows `.next` `EPERM`, and an unchanged unsandboxed retry succeeded. No live Railway deployment has been tested yet.
